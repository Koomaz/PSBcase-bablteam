# Серверные диалоги, диагностика и документы

API обслуживает одну общую рабочую область MVP. Все клиенты этого экземпляра видят одни диалоги. Учётных записей и разделения по пользователям в текущем прототипе нет. После подключения этих маршрутов фронтенд сможет заменить localStorage серверной историей. Stateless `/api/chat` продолжает принимать собственный `history`.

## Диалоги

| Метод | Ответ JSON |
|---|---|
| `GET /api/dialogs` | `{dialogs: [{id, title, updated_at, message_count}], request_id}` по убыванию updated_at |
| `POST /api/dialogs` | `201 {id, request_id}` |
| `GET /api/dialogs/{id}` | `{id, messages: [{role, content, kind, sources, created_at}], request_id}` |
| `POST /api/dialogs/{id}/messages` | Вход `{question: "…"}`, ответ `{kind, answer, sources, created_at, request_id}` |
| `PATCH /api/dialogs/{id}` | Вход `{title: "…"}`, ответ `{id, request_id}` |
| `DELETE /api/dialogs/{id}` | `{deleted: true, request_id}` |
| `DELETE /api/dialogs` | `{deleted: true, request_id}` |

Обёртки списка и сообщений оставляют место для request_id. ID — непрозрачная строка. Новый диалог создаётся пустым, название после первого успешного ответа берётся из вопроса, если пользователь ещё не переименовал диалог. Сообщения возвращаются по порядку. Время — ISO 8601 UTC. У пользовательского сообщения `kind=null` и `sources=[]`. Название до 120 символов, вопрос до 4000.

История для модели выбирается сервером из последних восьми сообщений, с ограничением до 4000 символов на реплику и суммарно до 12000. Это тот же контракт контекста, который применялся к stateless API. Полная сохранённая история не обрезается.

Вопрос и ответ сохраняются атомарно только после успешной генерации. Техническая ошибка не создаёт неполную пару, повтор допустим. Одновременная генерация для одного диалога получает `409 dialog_busy`, причина `concurrent_request`. Запросы разных диалогов независимы. Если диалог удалён во время генерации, завершение получает 404 и не восстанавливает данные. При аварийном завершении процесса блокировка освобождается по истечении бюджета вопроса с запасом 30 секунд. Повтор HTTP-запроса после уже успешного сохранения считается новым сообщением, ключ идемпотентности пока не предусмотрен.

SQLite хранится по `PSB_DB_PATH`, для обычного Python по умолчанию `state/dialogs.sqlite3`. Docker использует `/state/dialogs.sqlite3`, Compose монтирует постоянный том `dialog_data`. Обычный `docker compose down` сохраняет историю. `down -v` удалит том и историю. `data` с корпусом по-прежнему подключён только для чтения.

## Диагностика

Каждый HTTP-ответ имеет заголовок `X-Request-ID`. JSON API также содержит `request_id` на верхнем уровне. ID создаёт сервер, он не доверяет ID из входного заголовка. Ошибка имеет вид:

```json
{"request_id":"…","detail":{"code":"invalid_response","reason":"validation_failed","message":"Сервис генерации вернул некорректный ответ."}}
```

Основные причины `invalid_response` — `empty_content`, `malformed_response`, `validation_failed`, `numeric_citation`. Другие причины — `request_timeout`, `unauthorized`, `service_error`, `component_unavailable`, `not_found`, `validation_error`, `internal_error`.

Сервер пишет в stderr ID, порядковый номер вызова модели, разрешённое значение finish_reason, число попыток и число/категории замечаний валидатора. Текст вопросов, полные ответы, значения конфигурации, ключи и сообщения исключений не логируются. Категории замечаний — number, citation, length, other. Полные текстовые замечания могут содержать фрагменты данных и намеренно не выводятся. Журнал доступен через `docker compose logs backend`. Readiness означает локальную инициализацию, живой вызов модели в нём не выполняется.

## Полный документ

`GET /api/documents/{doc_id}` возвращает `{doc_id, doc_title, file_path, text, offset_encoding, request_id}`. Это исходный декодированный текст документа из того же корпуса, а не склейка чанков. `offset_encoding=unicode_codepoints`. Границы существующих источников `[char_start,char_end)` относятся к этому тексту. Интерфейс исправлен для выделения по кодовым точкам Unicode, включая символы за пределами BMP.

Путь к файлу от клиента не принимается. Разрешается только doc_id, загруженный из базы при старте. Неизвестный ID даёт 404 document_not_found. Корпус организаторов фиксирован. При его замене старые сохранённые источники требуют отдельной версионной схемы, поскольку ID ML1 не является хешем текста. До её добавления следует использовать отдельный экземпляр/том истории для другого корпуса.

Функция просмотра полного документа во фронтенде по-прежнему управляется `VITE_FEATURE_DOCUMENT_VIEWER` на этапе сборки. Миграция UI-диалогов с localStorage на новые маршруты остаётся отдельной задачей фронтенда.

## Проверка реализации

Пройдены 24 теста backend, включая новые проверки CRUD, восстановления истории в новом процессе приложения, изоляции диалогов, конфликтов, удаления во время генерации, освобождения блокировки после ошибки и восстановления истёкшей блокировки. Внешняя генерация в тестах имитируется. Отдельно прошли Docker-сборка, Compose-проверка API и SQLite-проверка сохранения диалога после реального перезапуска контейнера. Frontend TypeScript build и lint проходят. Проверка плоского ZIP во временной директории дала 18/18 строк без технических сбоев с тестовым прокси. Секреты и реальные ключи для проверки не использовались.
