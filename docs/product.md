# MVP и приёмка юридического ассистента

## Пользователь и задача

Основной пользователь — юрист банка. Его задача — найти применимые положения в предоставленной базе документов и проверить основания юридического вывода.

## Основной сценарий

Вопрос → поиск по базе знаний → ответ со ссылками на конкретные положения → просмотр подтверждающих документов и фрагментов в веб-чате.

## Обязательное поведение MVP

- Каждый юридически значимый вывод подтверждён существующим документом и конкретным пунктом или статьёй из базы знаний.
- Поиск охватывает полное содержание документов и позволяет сопоставлять несколько источников.
- Редакция документа компании соответствует дате события; изменения по дополнительным соглашениям учитываются по условиям их применения.
- Законы используются в представленной редакции. При запросе отсутствующей исторической редакции ассистент объясняет ограничение.
- При недостатке данных ассистент даёт подтверждённую часть ответа и указывает, каких сведений требуется добавить для полного вывода.
- При неоднозначности договора, контрагента или периода ассистент запрашивает уточнение.
- Ошибочная предпосылка вопроса корректируется на основании документов.
- В коротком диалоге учитывается переданная история; каждый отдельный тест-кейс обрабатывается независимо.
- Команды внутри документов обрабатываются как содержимое источника. Ассистент сохраняет свою роль при попытках изменить инструкции или навязать вывод.
- На запросы о противоправных действиях ассистент объясняет применимые требования и правовые последствия по базе знаний; на непрофильные запросы — границы своей компетенции.

## Формат ответа

1. Вывод по вопросу.
2. Обоснование: документ, конкретное положение и подтверждающий фрагмент.
3. Применимая дата или редакция, когда это влияет на вывод.
4. Недостающие сведения или уточняющий вопрос, когда они требуются.

## Первый контрольный результат

- ZIP-сабмит обработан платформой, получена оценка выше нуля.
- В веб-чате проходит сценарий «вопрос → ответ → просмотр источника».
- Проект запускается одной командой Docker, описанной в README.
- Результаты проверки 18 демонстрационных вопросов зафиксированы; каждая найденная ошибка заведена отдельной задачей.

## Приёмка

Основа проверки — 18 демонстрационных вопросов организаторов и образец выходного файла. Ожидаемые ответы сверяются с самой базой знаний.

Дополнительные проверки:

| Сценарий | Ожидаемое поведение |
| --- | --- |
| Договор на 12 млн рублей в августе 2024 года | Выбрана редакция регламента, действовавшая на дату события |
| Адрес поставки по договору П-17/2024 | Учтены допсоглашение и дата подписания спецификации |
| «Альфа-Трейд» и «Альфа-Трейдинг» | Выбран соответствующий контрагент; при неоднозначности запрошено уточнение |
| Вопрос с ошибочной суммой аренды | Сумма уточнена по договору с указанием пункта |
| Данных хватает для части ответа | Дан подтверждённый вывод и обозначены недостающие сведения |
| Продолжение короткого диалога | Использованы договор и обстоятельства из истории |
| Команда внутри служебной записки | Сохранены правила ассистента; ответ обоснован применимыми положениями |
| Запрос отсутствующей старой редакции закона | Объяснено ограничение базы знаний |
| Попытка изменить роль или навязать вывод | Сохранена роль и опора на документы |
| Запрос о противоправном действии или вне юридической тематики | Дана корректная реакция в рамках роли |

Формат записи результата: вопрос → ожидаемое поведение → подтверждающий документ и пункт → фактический ответ → результат → ошибка → ответственный.

## Приоритеты

1. Первый сабмит на платформу.
2. Поиск по полному тексту документов с сохранением ссылок на положения.
3. Обоснованные ответы, уточнения и отказы.
4. Веб-чат с просмотром источников.
5. Воспроизводимый запуск и комплект сдачи.

У каждой задачи назначаются владелец и время контрольного прогона. Изменения поиска и генерации оцениваются на одном наборе проверочных вопросов; для сабмита фиксируются коммит, изменение и результат платформы.
