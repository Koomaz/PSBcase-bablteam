# PSBcase-bablteam

Юридический ассистент по предоставленной базе документов. Пакетный сабмит и HTTP API используют общий конвейер: ML1 выполняет локальный поиск, ML2 формирует и валидирует ответ с ссылками. Backend читает входные данные платформы, передаёт историю диалога, проверяет источники, собирает CSV и ZIP, а также предоставляет HTTP API для будущего фронтенда.

Проект подготовлен не полностью: фронтенда в репозитории пока нет, реальная генерация через DeepSeek и отправка ZIP на платформу не проверены. Актуальная граница проверки описана в [отчёте проверки](docs/backend-verification.md).

## Локальная подготовка

Для проверок использовался Python 3.12. Из архива организаторов возьмите `knowledge-base.zip` и `demo_questions.csv`. Положите базу в `data/knowledge-base.zip`, а демо-вопросы скопируйте в `data/questions.csv`. При необходимости укажите другой каталог через `DATA_DIR`.

```sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install -r requirements-api.txt
python -m unittest discover -s tests -v
```

## Сабмит

```sh
python scripts/build_submission.py
python tests/verify_submission.py dist/submission.zip data/questions.csv data/knowledge-base.zip
```

Вторая команда распаковывает ZIP во временный каталог, запускает его на 18 демо-вопросах с локальной имитацией прокси, проверяет CSV и измеряет время и пиковую память процесса. Для запуска с доступным прокси задайте в окружении `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`, затем выполните `python solution.py`. Результат появится в текущем рабочем каталоге как `submission.csv`. Для запуска только сабмита достаточно зависимостей из `requirements.txt`.

Когда команда готова использовать попытку, загрузите `dist/submission.zip` в раздел автоматических сабмитов секции ПСБ. Дождитесь результата проверки и запишите версию исходников, время, оценку и обезличенную диагностику. Платформа сама предоставляет базу, вопросы и настройки своего прокси. [Регламент, §§ 2–6 и 9](https://docs.google.com/document/d/1GjOSBr6xtiweDrMI5Kvcnug4wcbHCzg7n5TJ4UBnuxg/edit)

## API для чата

При заданных переменных прокси и доступной базе:

```sh
python -m uvicorn web_api:app --host 127.0.0.1 --port 8000
```

- `GET /health/ready` проверяет инициализацию конфигурации и локального индекса.
- `POST /api/chat` принимает вопрос и историю. Ответ содержит текст и структурированные ссылки.
- `GET /api/sources/{chunk_id}` возвращает точный текст фрагмента из индекса.
- Интерактивная схема OpenAPI доступна на `http://127.0.0.1:8000/docs`.

Backend использует командный ML2 с обязательной настройкой прокси. При отсутствии настройки или компонентов API сообщает о недоступности. Локальные заглушки из тестов не попадают в ZIP. Для локального прототипа нужны `LLM_BASE_URL`, `LLM_API_KEY` и `LLM_MODEL`; допустимы совместимые имена `OPENAI_*` / `GEN_MODEL`. Переменные, источники и черновой контракт фронтенда описаны в [документе интеграции](docs/backend-contract.md).

## Docker

Нужны Docker Engine с Compose и база организаторов в `data/knowledge-base.zip`. Образ использует Python 3.12.12 с закреплённым digest и версии из `requirements-api.txt`. Индекс ML1 строится в памяти при запуске. Контейнер работает от непривилегированного пользователя, база подключается только для чтения.

Скопируйте `.env.example` в `.env` и локально заполните адрес прокси, существующий ключ и точный идентификатор модели. По регламенту платформа предоставляет прокси и DeepSeek V4.1 Flash; эти модель и адрес локально не проверены. Адрес и доступ для прототипа команда получает отдельно. Не передавайте ключ в Git, ZIP, Docker-образ или сообщения. `.env` исключён из Git и Docker-контекста; при запуске через Compose значения читаются из него, а при прямом запуске Python — из окружения процесса.

Проверьте конфигурацию перед запуском, не печатая значение ключа:

```sh
test -n "$LLM_BASE_URL" && test -n "$LLM_API_KEY" && test -n "$LLM_MODEL"
docker compose config --quiet
```

После подготовки конфигурации запустите одной командой:

```sh
docker compose up --build -d --wait
```

`--wait` завершится успешно только после настройки прокси: без `LLM_*` контейнер запускается, но `/health/ready` возвращает 503, что является корректным сигналом недоступности генерации. Для осмотра образа без модели используйте `docker compose up --build -d` без `--wait` и проверяйте подробности через `docker compose ps` и `docker compose logs backend`.

API доступен на http://127.0.0.1:8000, интерактивная схема — на http://127.0.0.1:8000/docs. `PSB_PORT` меняет порт на хосте, `PSB_DATA_DIR` — каталог базы. `DATA_DIR` внутри контейнера равен `/data`. Если прокси работает на хосте, используйте `host.docker.internal` вместо `localhost`. Остановка выполняется командой `docker compose down`.

Проверьте основной сценарий в `/docs`: отправьте вопрос через `/api/chat`, возьмите `chunk_id` из ответа и откройте `/api/sources/{chunk_id}`. Убедитесь, что найденный фрагмент существует и содержит основание ответа. Следующий запрос передайте вместе с предыдущими сообщениями в `history`; без `history` запрос должен обрабатываться независимо.

Для воспроизводимой контейнерной проверки с временной имитацией прокси:

```sh
python tests/verify_docker.py
```

Проверка сама создаёт отдельный проект Compose и удаляет его после завершения. Она требует предварительной установки зависимостей API и доступной базы, но использует временную имитацию модели. Это проверка транспорта, поиска и контракта, а не качества ответов DeepSeek. Полный прогон с реальной моделью требует действующих настроек прокси. Результаты проверок и ограничения приведены в [отчёте проверки](docs/backend-verification.md).
